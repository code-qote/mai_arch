## Вариант 22: Система управления событиями

## М8О-107СВ-25 Глушин Никита


### 1. Описание системы и требования к API
Система предназначена для управления мероприятиями (создание событий, поиск, бронирование и продажа билетов).
API системы разделено на следующие домены:
* **Пользователи:** Создание профиля, поиск пользователя по логину.
* **События:** Создание события, получение данных о редактируемом/просматриваемом событии, полнотекстовый поиск.
* **Бронирование:** Резервирование мест на выбранное событие, обработка транзакций, отмена регистрации, получение списка участников события и списка событий конкретного пользователя.

### 2. Пользователи и внешние системы
* **Пользователь системы:** Организатор мероприятий (создание, мониторинг) или участник (поиск, покупка билетов).
* **Email-сервис:** Внешняя система для транзакционной рассылки электронных билетовв.
* **Платежный шлюз:** Внешняя система (эквайринг) для проведения платежей с банковских карт (например, Stripe или ЮKassa).

### 3 и 4. Контейнеры и технологии
Архитектура системы базируется на микросервисном подходе. Взаимодействие со стороны клиента осуществляется по протоколу HTTP/REST, межсервисное взаимодействие реализовано через gRPC.

Перечень контейнеров (C2):
1. **Web Application (React/TS)** — фронтенд.
2. **API Gateway (Envoy)** — единая точка входа. Осуществляет маршрутизацию REST API запросов и их трансляцию в gRPC для внутренних сервисов.
3. **Search Service (c++ (userver))** — микросервис полнотекстового поиска событий.
4. **User Service (c++ (userver))** — микросервис управления профилями пользователей.
5. **Event Service (c++ (userver))** — микросервис управления каталогом событий и инвентаризацией расписаний/мест.
6. **Book Service (c++ (userver))** — микросервис управления процессом бронирования и оркестрации платежей.
7. **Event Cache (Redis)** — in-memory хранилище для быстрого доступа к статичным метаданным событий (тексты, описания).
8. **Elasticsearch** — поисковый движок для обеспечения быстрого многокритериального поиска по каталогу.
9. **Database (PostgreSQL)** — единая реляционная СУБД для обеспечения транзакционной целостности данных (ACID). Содержит схемы пользователей, событий и реестр билетов.

### 5. Архитектурно значимый сценарий (Dynamic View)
Рассматривается полный хронологический цикл обработки заказа, объединенный в единое представление (Dynamic Flow). Цикл разделен на 3 логических этапа:

1. **Этап "Поиск":** Пользователь вводит запрос. Запрос маршрутизируется в `Search Service`, который выполняет выборку по индексу в `Elasticsearch` и возвращает список релевантных событий.
2. **Этап "Выбор мест":** Пользователь открывает карточку события. `Event Service` читает текстовое описание из кэша (`Redis`), после чего выполняет запрос актуального наличия свободных мест напрямую из СУБД (`PostgreSQL`), чтобы избежать проблемы "грязного чтения".
3. **Этап "Бронирование и Оплата":** Пользователь инициирует оплату. Процесс оркестрируется сервисом `Book Service`:
   - Выполняется строгая проверка и транзакционная блокировка запрашиваемых мест через `Event Service`.
   - В БД создается запись о брони в статусе "Ожидание".
   - Выполняется синхронный вызов внешнего `Платежного шлюза`.
   - При успешном списании средств статус брони в БД обновляется на "Успешно".
   - Асинхронно вызываются внешние интеграции (`Email-сервис`) для доставки билетов и чеков пользователю.
